# Sparkle integration

Build 20 includes Sparkle 2.10.0 through an exact SwiftPM dependency and lockfile.
`UpdateService` retains one standard updater, starts it on the main thread only
when valid release configuration is present, and observes Sparkle's properties
for the settings UI. It does not maintain a second scheduler or reset users'
update choices on launch. Check for Updates is available in both menus and
Settings → About. Without release configuration these controls are disabled,
and no Sparkle requests, permission prompts or helper processes are started.

The source repository is [nityantmukherjee777-ctrl/notch](https://github.com/nityantmukherjee777-ctrl/notch).
Binary release hosting, DMG packaging and live update activation remain deferred
at the user's request. This integration does not require an Apple Developer
membership. The current build retains the local signing identity. Developer ID
and notarization are separate distribution choices; the project's existing
public-release gate still requires them for a verified public binary.

The personal certificate has no Apple Team ID. macOS's Hardened Runtime library
validation consequently rejects the embedded Sparkle framework at launch, even
when both app and framework have the same personal signature. A personal build
therefore requires an explicitly approved host-only library-validation exception:
`NOTCH_ALLOW_LOCAL_SPARKLE=1 ./scripts/build.sh`. This permits loading libraries
that do not carry an Apple Team ID; it does not disable macOS Gatekeeper or alter
privacy grants. Helpers keep upstream entitlements, and all signatures are still
verified. `NOTCH_PUBLIC_RELEASE=1` rejects this exception. Apple-signed builds do
not add it. The user approved this exception for the current personal build;
the explicit build flag prevents it from being silently added to other builds.

## When release hosting is ready

1. Choose a stable HTTPS appcast URL. A future GitHub release can host
   `appcast.xml` at `https://github.com/OWNER/REPO/releases/latest/download/appcast.xml`.
   This is an example, not a configured endpoint. Each appcast enclosure must
   point to an immutable versioned release asset, not a moving latest download.
2. Generate one Ed25519 signing key using the official tool downloaded by
   SwiftPM: `.build/artifacts/sparkle/Sparkle/bin/generate_keys`. It stores the
   private key in macOS Keychain and prints the public key. Back up that private
   key securely; never commit it, put it in an app bundle or publish it on GitHub.
   No key has been generated by this integration.
3. Provide only the public configuration when building:

   ```sh
   export NOTCH_UPDATE_FEED_URL='https://your-host/appcast.xml'
   export NOTCH_SPARKLE_PUBLIC_KEY='YOUR_BASE64_PUBLIC_KEY'
   ./scripts/build.sh
   ```

   `configure-updates.py` inserts `SUFeedURL` and `SUPublicEDKey` into the staged
   Info.plist before signing. Partial, insecure or malformed configuration fails
   the build without replacing the installed app. Neither variable is a secret.
   Leaving both unset builds an inactive updater; there are no placeholder URLs.
4. Keep `CFBundleIdentifier` and the retained app signing identity stable. Raise
   the integer `CFBundleVersion` for every release; Sparkle compares build numbers,
   not just the displayed marketing version. Resolve the final public identity
   before shipping to others. Once chosen, do not change it between updates.
5. Archive the app with framework symlinks and permissions intact, then use
   `.build/artifacts/sparkle/Sparkle/bin/generate_appcast` to sign the archive,
   appcast and release notes with the retained Ed25519 key. Read its `--help` for
   download URL options. Upload the complete signed feed and matching archive;
   editing the XML or release notes after signing invalidates their signatures.

The signed Info.plist defaults to hourly automatic checks and automatic download
and installation, as requested. Users can turn either setting off. Verified
updates download in the background and install when the app quits or relaunches;
active widgets are not forcibly interrupted when a release appears. Sparkle uses
its normal scheduling and persists the user's choices. The app does not force checks on wake or repeatedly
at launch. `SUVerifyUpdateBeforeExtraction` and `SURequireSignedFeed` are enabled.
System profiling is disabled. Sparkle's standard UI handles release notes,
download errors, user cancellation, installation and relaunch; app termination
uses the existing service shutdown so audio taps and Keep Awake are released.

## Packaging

The CLT build uses `ditto` to embed the framework and helper binaries, preserving
executable bits and symlinks. `sign-app.py` re-signs helpers inside out, preserving
their upstream entitlements, then signs Sparkle, MediaRemoteAdapter and Notch.
The host's Automation entitlement is not copied to helpers. Runtime framework
lookup uses `@executable_path/../Frameworks`. Only an explicitly approved personal
build adds the host-only library-validation exception described above.
Apple-signed public builds retain library validation. No App Transport Security
exception or new macOS privacy permission is added.
The Sparkle licence is copied into the app's Resources folder.

## Validation

```sh
python3 scripts/test-update-configuration.py
python3 scripts/test-signing-policy.py
./scripts/test.sh
# Explicit fallback only for the current mismatched CLT / Testing framework:
python3 scripts/test-compatible.py
codesign --verify --deep --strict dist/Notch.app
```

Before publishing, test an actual installed old build updating to a newer build
through the hosted, signed appcast. Include manual check, automatic checks off,
automatic installation on/off, no available update, offline feed, cancelled
download, invalid archive and feed signatures, installation from Applications,
read-only DMG handling, relaunch, and retained preferences, timer and macOS
permissions. Live delivery and installation cannot be validated until a real
feed, signing key and two release builds exist.
